# AGHARAS VISION — PostgreSQL to Hostinger MySQL Feasibility

> **Historical feasibility snapshot only. Superseded on 9 November 2026 by the isolated implementation and real MariaDB 11.4.8 verification documented in [`HOSTINGER_MARIADB_CONVERSION.md`](HOSTINGER_MARIADB_CONVERSION.md).** The original PostgreSQL repository and its database were not modified. Hostinger account-specific verification and adoption remain pending.

**Assessment date:** 2026-11-09
**Scope:** Read-only feasibility review. No application, database, migration, or deployment changes were made for a MySQL conversion.
**Verdict:** **MYSQL MIGRATION NOT RECOMMENDED (implementation gate not passed).** This is a stop-for-now verdict, not a finding that migration is inherently impossible.

## Gate decision

The existing application must remain PostgreSQL-backed. Prisma 6 documents support for both MySQL and MariaDB, so a migration appears technically possible with a separate schema/migration history and explicit adaptations. However, the required genuine isolated MySQL test server is not available in this environment: no `mysql`, `mysqld`, MariaDB executable, Docker executable, matching Windows service, or listener on ports 3306/33060 was found. The current `.env` has a `DATABASE_URL`; its value was deliberately not inspected, printed, or used. No database connection or write was attempted.

Consequently, transaction equivalence, MySQL migration initialization, Hostinger compatibility, and critical business workflows cannot be demonstrated. In particular, the current checkout/optical shared lock depends on PostgreSQL advisory-lock semantics. The atomic conditional stock decrement is promising but is not a substitute for testing the combined workflow against InnoDB under contention. Do not start implementation or target any existing database until a disposable, identified MySQL/MariaDB server is supplied and the lock design is validated.

## Business workflow coverage and integrity

This was a source/schema review, not a MySQL regression run. Prisma Client calls and transaction sites were inspected for checkout, optical decisions, admin order/catalog workflows, and the email outbox. The following are **not verified on MySQL**: catalogue search and filters, product/variant CRUD, CMS/store/settings writes, owner authorization, prescription access/privacy, guest checkout, COD, coupon limits, order status history, inventory administration, optical approval enforcement, cron/outbox worker races, and storage metadata. No claim of MySQL workflow compatibility is made.

The existing order path calculates prices server-side before the transaction and persists integer cent totals plus item snapshots. It applies an atomic guarded decrement within a transaction, followed by transactional movement/order/related rows, and enqueues email work before commit. Those are important invariants to preserve, but the advisory lock currently coordinates optical rule edits with checkout; replacing that coordination without genuine concurrency testing would create an unacceptable optical/checkout risk. Progressive lens options must remain disabled for new sales, and no ADD/EP or automatic clinical plausibility gate should be introduced as a database-migration shortcut.

## Hostinger and Prisma documentation reviewed

- Prisma ORM **v6** MySQL/MariaDB connector: <https://www.prisma.io/docs/orm/v6/overview/databases/mysql> — states that the MySQL connector supports MySQL and MariaDB; documents `mysql://USER:PASSWORD@HOST:PORT/DATABASE`, Prisma v6 pool/timeout URL arguments, MySQL JSON support (5.7+), `DateTime` → `DATETIME(3)`, `Decimal` mappings, and migration privileges/shadow database considerations.
- Hostinger, *How to connect PHP to MySQL*: <https://www.hostinger.com/tutorials/how-to-connect-php-to-mysql/> — says same-host applications commonly use `localhost`; remote host details must be confirmed with provider/dashboard.
- Hostinger, *MariaDB vs MySQL*: <https://www.hostinger.com/tutorials/mariadb-vs-mysql/> — states regular, Cloud, and WordPress hosting use MariaDB and recommends checking installed version in hPanel. This does not establish this project's actual Business account version or Prisma runtime compatibility.
- Hostinger database management guidance: <https://www.hostinger.com/tutorials/wordpress-database/> — directs users to dashboard for the actual database name and user; those values are account-specific.

The user-provided connection string is a template only. Do not assume the final Hostinger endpoint is `127.0.0.1`, that the account uses MySQL rather than MariaDB, or that the web plan allows remote DB access or grants migration/shadow-database privileges. Do not invent credentials or rely on root privileges.

## Safe next gate (not authorized or performed here)

1. Supply/commission a disposable local MySQL or MariaDB instance isolated from all existing PostgreSQL/demo systems; identify server version, endpoint, database, and user before writes. Do not reuse the current `.env` database URL.
2. In a separate copy or safe worktree, design a MySQL schema representation for all four scalar lists and a transaction-scoped coordination scheme that works across optical-review and checkout using the same InnoDB locking protocol.
3. Establish a new MySQL migration baseline and preserve the PostgreSQL migrations unchanged in the original project.
4. Apply migrations only to a fresh disposable database; test constraint enforcement, collation, datetime, decimal, JSON/null, rollback, delete behavior, duplicate idempotency, last-item races, optical review races, and worker claims; inspect persisted records.
5. Only after critical regression and production-runtime/version compatibility pass, reconsider the gate. Any future business-data conversion needs explicit authorization and a separate audited export/import/reconciliation plan.
